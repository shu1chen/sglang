3. Architecture Comparison

Baseline — brgemm + parallel_2d

parallel_2d(MB, NB) ← all threads work on 2D tile grid concurrently └─ loop_2d(mb, nb, chunk_size) ← cache-blocked inner loop ├─ copy_stub: A[BLOCK_M, K] ← gather ≤32 rows into thread-local buffer (224 KB) ├─ brgemm(A, B0, C0) ← JIT microkernel, [≤32, 7168] × [7168, 32] → [≤32, 32] s32 ├─ brgemm(A, B1, C1) ← same, for up-projection half └─ silu_and_mul(C0, C1 → ic1) ← fused: C0,C1 are 4 KB each, still hot in L1 cache Key property: weights in native VNNI format [K/4, BLOCK_N, 4] — brgemm reads directly. Per-tile s32 output: 32 × 32 × 4 = 4 KB → fits in L1 (48 KB per core). No dispatch overhead: brgemm is a direct function-pointer call to JIT'd AMX code. No inter-expert barriers: all experts' tiles distributed across threads simultaneously.

V1 — Sequential Expert + oneDNN matmul

for (expert : expert_batches) ← SEQUENTIAL over experts (serialized!) ├─ gather A: [m_size, K] → A_padded ← copy up to 1 MB of activations ├─ w1_prim.execute(A, B_cached, C_combined) ← oneDNN matmul [padded_m, K] × [K, 2N] │ └─ s.wait() ← BARRIER: wait for all oneDNN internal threads ├─ at::parallel_for(scale_and_silu_mul) ← separate pass over [m_size, 2N] s32 output │ ← re-reads 2.6 MB of s32 data from memory ├─ w2_prim.execute(A, B_cached, C_s32) ← oneDNN matmul [padded_m, N] × [N, K] │ └─ s.wait() ← BARRIER again └─ at::parallel_for(scale_and_weight_fused) ← separate pass over [m_size, K] s32 output Key property: ONE matmul per expert for the entire N dimension. Weight format: VNNI unpacked → [N, K] plain → reordered to BA16a64b4a (cached). Per-expert s32 output: padded_m × 2N × 4 = 160 × 4096 × 4 = 2.6 MB → exceeds L2 (2 MB). Barriers per kernel call: 2 barriers/expert × E experts × 2 stages = 4E barriers total.

V2 — parallel_2d + oneDNN matmul Tiles

parallel_2d(MB, NB_wide) ← same 2D grid as baseline, NB_wide = N/64 └─ loop_2d(mb, nbw, chunk_size) ├─ copy_stub: A[BLOCK_M, K] ← gather ≤32 rows (same as baseline) ├─ dnnl_primitive_execute(A, B_cached, C_fused) │ ← matmul [32, 7168] × [7168, 128] → [32, 128] s32 (gate+up fused, 2×64) └─ silu_and_mul_strided(C_fused → ic1) ← post-processing with stride=128 ← C_fused = 32 × 128 × 4 = 16 KB Key property: same parallelism as baseline — no serialization. Weight format: VNNI unpacked → plain → oneDNN any format (cached). Per-tile s32 output: 32 × 128 × 4 = 16 KB → fits in L1 but 4× larger than baseline's 4 KB. Dispatch overhead: ~100-200 ns per dnnl_primitive_execute call × many tiles.

4. Stage-by-Stage Kernel Pipeline

All three implementations share the same 5-stage pipeline. The differences are only in Stages 1 and 2 (the GEMM + post-processing stages).

StageOperationDimensionsShared?
0Quantize input bf16 → uint8[M, K]✓ Identical
1Gate+Up GEMM + silu_and_mul[M·topk, K] × [K, 2N]✗ Different
1.5Quantize ic1 bf16 → uint8[M·topk, N]✓ Identical
2Down-proj GEMM + scale + scatter[M·topk, N] × [N, K]✗ Different
3Reduce sum over topk[M, topk, K] → [M, K]✓ Identical

Since Stages 0, 1.5, and 3 are identical, all performance differences come from Stages 1 and 2.

5. Root Cause Analysis: V1 — Sequential Expert Loop

Problem 1: Sequential Expert Processing Destroys Parallelism

V1 processes experts one at a time in a for (batch : expert_batches) loop. Each expert's matmul uses oneDNN's internal threading (all 43 cores), but experts are serialized.

Metric (M=384, E=8, topk=3)BaselineV1
Matmul calls in Stage 1~2700 brgemm calls distributed across 43 threads, zero barriers8 sequential matmul calls, each with s.wait() barrier
Matmul calls in Stage 2~2700 brgemm calls, zero barriers8 sequential matmul calls, each with s.wait() barrier
Total thread barriers2 (#pragma omp parallel for Stage 1 and Stage 2)32+ (8 experts × 2 stages × 2 barriers/stage)

Each s.wait() and each at::parallel_for entry/exit involves an OpenMP fork-join barrier. On 43 cores, a barrier costs ~2-5 µs. With 32+ barriers, this alone adds ~0.1–0.2 ms.

Problem 2: Massive Intermediate Buffer Thrashing

V1's matmul outputs the entire expert's result before post-processing it:

BufferBaseline per tileV1 per expertRatio
Stage 1 s32 output (C0 + C1) 32 × 32 × 4 × 2 = 8 KB
(fits in L1, 48 KB)		 160 × 4096 × 4 = 2,621 KB
(exceeds L2, 2048 KB)		 328×
Stage 2 s32 output 32 × 32 × 4 = 4 KB 160 × 7168 × 4 = 4,587 KB 1147×

In the baseline, silu_and_mul consumes C0/C1 immediately while they're in L1. In V1, the s32 output is written to DRAM by oneDNN, then the separate at::parallel_for(scale_and_silu_mul_fused) re-reads it from DRAM — a full round-trip through the memory hierarchy.

Problem 3: Activation Gather Overhead

V1 gathers all tokens for an expert into a contiguous buffer before the matmul:

Metric (M=384, E=8, topk=3)BaselineV1
Gather size per call≤32 × 7168 = 224 KB~144 × 7168 = 1,008 KB
Who gathersEach thread gathers its own BLOCK_M rowsSingle-threaded or parallel_for (extra fork-join)
Contiguity checkNone neededO(m_size) loop to check contiguity + fallback gather

Problem 4: Wasted Computation on Padded Rows

V1 pads m_size to the next BLOCK_M=32 multiple (padded_m). For an expert with 144 tokens, padded_m = 160, wasting 16 rows × full K × 2N = ~940M int8 ops per expert. With 8 experts, total wasted: ~7.5G ops (~5% of useful compute).

Why M=384, E=8, topk=5 Is the Only Near-Parity Case

With topk=5: total tokens = 1920, each expert gets ~240 tokens, padded to 256. The matmul shape [256, 7168] × [7168, 4096] is large enough that:

  • AMX tile reuse is high (256 rows ÷ 16 = 16 M-tiles, good amortization).
  • The barrier cost (~0.2 ms) is small relative to total compute (~14 ms).
  • oneDNN's internal blocking can effectively use all 43 cores.
  • Padding waste is only 256-240 = 16 rows, or 6.7%.

6. Root Cause Analysis: V2 — parallel_2d oneDNN Blocks

V2 preserves the baseline's parallel_2d parallelism structure, so it avoids V1's serialization problem. The remaining gaps come from three sources:

Source 1: Per-Tile Dispatch Overhead

Metric (M=384, E=8, topk=3)BaselineV2
Stage 1 tiles per threadMB × NB / 42 ≈ 36 × 64 / 42 ≈ 55 tilesMB × NB_wide / 42 ≈ 36 × 32 / 42 ≈ 27 tiles
GEMM calls per tile2 brgemm calls (B0, B1)1 dnnl_primitive_execute call (fused gate+up)
Cost per call~0 ns (JIT function pointer)~100-200 ns (primitive dispatch, arg packing)
Total dispatch overhead~0 ms~0.03-0.06 ms per stage

This is minor but measurable for the E=1 case where total compute is only ~1 ms.

Source 2: Wider s32 Output Buffer (L1 Pressure)

MetricBaselineV2
Stage 1 s32 output per tile32 × 32 × 4 × 2 = 8 KB32 × 128 × 4 = 16 KB (fused gate+up)
L1 cache residency8 KB / 48 KB = 17%16 KB / 48 KB = 33%
Post-processing strideBLOCK_N = 32 (tight)fused_matmul_n = 128 (strided reads from wider buffer)

silu_and_mul_strided reads gate values at offset s * BLOCK_N and up values at offset wide_n + s * BLOCK_N within a row of width 2 * actual_matmul_n = 128. This strided access pattern is less cache-friendly than the baseline's tight BLOCK_N=32 buffers.

Source 3: Weight Format Double-Conversion

Weights are stored in VNNI format [K/4, BLOCK_N, 4], which is the native AMX layout. V2 unpacks them to plain [K, N], then oneDNN re-packs into its own optimal format via format_tag::any. This is a VNNI → plain → oneDNN-internal double-conversion. The reorder is amortized (cached), but the resulting format may not be more efficient than the original VNNI — and the extra memory for the cached reordered weights adds to memory footprint.

Why E=1, topk=1 Shows 25% Regression

With E=1, topk=1, M=384: there is exactly one expert processing all 384 tokens. MB = 384/32 = 12, NB_wide = 2048/64 = 32. Total Stage 1 tiles = 12 × 32 = 384. Total compute: 384 × 7168 × 4096 × 2 = ~22.6G ops. At ~43 cores × ~2 TOPS each ≈ 86 TOPS, the pure compute takes ~0.26 ms. The actual measured time is 1.15 ms (baseline) vs 1.44 ms (V2), so compute is only ~23% of total time. The remaining ~77% is memory bandwidth, quantization, and overhead — where V2's per-tile dispatch and wider buffers have outsized impact.

Why E=8, topk=5 Shows 10% Regression

With topk=5, total tokens = 1920, MB = 60. Each thread in parallel_2d(60, 32) processes more tiles. The L2 cache blocking via loop_2d uses chunk_size = fused_matmul_n × K = 128 × 7168 = 917,504 bytes. The get_cache_blocks function computes: L2_size/2 / chunk_size = 1,048,576 / 917,504 = 1 block. This means no N-blocking reuse — each tile's weight data is fetched from memory independently. In the baseline, chunk_size = BLOCK_N × K × 2 = 32 × 7168 × 2 = 458,752 bytes, giving 1,048,576 / 458,752 = 2 cache blocks — enabling weight reuse across two N-blocks. This difference in L2 blocking efficiency explains V2's regression on this shape.

8. Why oneDNN matmul Cannot Beat brgemm Here

The Fundamental Constraint: Same AMX Hardware

Both brgemm and oneDNN matmul ultimately execute the same AMX TDPBUSD instructions. The difference is only in the software overhead around those instructions. For the matmul shapes in MoE, AMX throughput is not the bottleneck.

Per-Tile Arithmetic Intensity Analysis

For a single Stage 1 tile (baseline: [32, 7168] × [7168, 32]):

MetricValue
Compute (int8 ops)2 × 32 × 32 × 7168 = 14.7M ops
Weight data read32 × 7168 × 1 byte = 224 KB
Activation data read32 × 7168 × 1 byte = 224 KB
Output data write32 × 32 × 4 bytes = 4 KB
Arithmetic intensity14.7M / 452 KB ≈ 32.5 ops/byte
AMX peak (1 core, int8)~2 TOPS
L2 bandwidth (1 core)~50 GB/s
Compute-limited time14.7M / 2T = 7.4 µs
Memory-limited time452 KB / 50 GB/s = 9.0 µs

The tile is memory-bandwidth limited (9.0 µs > 7.4 µs). A "better AMX blocking strategy" from oneDNN cannot help because AMX is already waiting on memory. The roofline intersection is at ~40 ops/byte; we're at 32.5.

The Theoretical Upside of oneDNN — and Why It Doesn't Apply Here

oneDNN matmul excels when:

  • The caller doesn't block — oneDNN can choose its own M/N/K tiling globally. In MoE, parallel_2d/loop_2d already tiles the problem externally.
  • Weight format is suboptimal — oneDNN's format_tag::any can find a better layout. In MoE, weights are already in VNNI format, which is what AMX consumes natively.
  • Post-ops are fused — oneDNN can fuse bias, eltwise (ReLU), etc. into the matmul. In MoE, silu_and_mul involves two matmul outputs (gate and up) — not expressible as a standard oneDNN post-op.
  • M is large — oneDNN's internal threading and blocking shine for large matrices. In MoE, the per-tile M is capped at BLOCK_M=32.

None of these conditions are met in the MoE kernel.

Winner

Near-optimal for MoE: zero dispatch overhead, native VNNI weights, L1-fused post-processing, fine-grained 2D parallelism, no inter-expert barriers.

V1 — Sequential Expert

+39-56%

Fundamentally flawed: sequential expert processing, L2-busting intermediate buffers, excessive barriers, large gather overhead. Not salvageable without architectural redesign.

V2 — parallel_2d Block

Correct parallelism, but per-tile dispatch overhead and wider buffers add up. Cannot outperform brgemm — at best matches it, at worst 25% slower.

Is There Room for oneDNN to Beat the Baseline?

Potential OptimizationFeasibilityExpected Gain
Fuse silu_and_mul as oneDNN post-op Infeasible — silu_and_mul needs two matmul outputs (gate, up); not a standard post-op Would save ~0.4 ms if possible
Increase MATMUL_N to full N Risky — fewer dispatches but worse L2 blocking for K-streaming ~0.03 ms dispatch savings, offset by cache misses
Call oneDNN once per expert (V1 approach with better parallelism) Impractical — requires restructuring the entire parallel decomposition Cannot match baseline's fused post-processing
Use oneDNN brgemm API directly Possible — but this is exactly what the baseline already does via PyTorch's cpublas::brgemm 0% — same code path

Final Verdict

There is no viable path for oneDNN matmul to outperform the brgemm baseline for this MoE int8 kernel.

The baseline's architecture — brgemm microkernels operating on small VNNI-format tiles with L1-fused post-processing in a fine-grained 2D parallel decomposition — is the optimal design for MoE on AMX hardware. oneDNN matmul adds dispatch overhead, requires weight format conversion, and separates GEMM from post-processing, all with no compensating benefit since the core AMX compute is identical.

oneDNN matmul is designed for large, standalone GEMM problems where its internal blocking, threading, and format selection provide value. In MoE, the GEMM is already decomposed into small, cache-blocked tiles with fused post-processing — exactly the scenario where a low-level primitive like brgemm excels and a high-level API like matmul adds overhead without compensating benefit.
